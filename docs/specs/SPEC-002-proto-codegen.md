# SPEC-002 — Contratto Protobuf (D7): codegen Go/Python + breaking-change check
Stato: verified
Task-tree: T0.2 · Servizio: contracts/proto (genera in libs/go, libs/py) · ADD: Modulo 3 — Deliverable D7
Contratti: contracts/proto/eci/retrieval/v1/retrieval.proto (già committato, Step 2 — NON modificarlo in questo task)

## 1. Obiettivo
Rendere `retrieval.proto` (D7) buildabile: lint e breaking-change check via `buf`, generazione degli stub gRPC Go (server+client) e dei tipi/stub gRPC Python, entrambi in directory generate chiaramente marcate, riutilizzabili dai servizi delle fasi successive senza ulteriore lavoro di wiring.

## 2. Interfaccia

File da creare:
- `contracts/buf.yaml` — config lint (`DEFAULT` ruleset) + breaking (categoria `WIRE_JSON` come minimo, idealmente `FILE`).
- `contracts/buf.gen.yaml` — due plugin per Go: `protoc-gen-go` (messaggi) e `protoc-gen-go-grpc` (servizio), output in `libs/go/eci/retrieval/v1/`.
- Per Python: **non tramite buf** (maturità inferiore per grpc Python) — comando esplicito via `python -m grpc_tools.protoc` invocato dal Taskfile, output in `libs/py/eci_core/retrieval/v1/` (genera `retrieval_pb2.py` e `retrieval_pb2_grpc.py`).
- Header standard in testa a ogni file generato: `# Code generated by buf/grpc_tools. DO NOT EDIT.` (o equivalente per linguaggio) — se il tool non lo appone automaticamente, aggiungerlo in post-processing dello script Taskfile.

Target Taskfile da implementare (sostituiscono i placeholder di SPEC-001):
- `task proto:gen` → esegue `buf generate` (Go) + il comando `grpc_tools.protoc` (Python) da `contracts/`.
- `task proto:breaking` → `buf breaking --against '.git#branch=main,subdir=contracts'`.
- `task proto:lint` → `buf lint` (nuovo target, aggiungerlo alla tabella dei target).

## 3. Comportamento (scenari)

1. **Dato** `retrieval.proto` in `contracts/proto/`, **quando** eseguo `task proto:gen`, **allora** vengono creati gli stub in `libs/go/eci/retrieval/v1/` e `libs/py/eci_core/retrieval/v1/` senza errori, ciascuno con l'header "DO NOT EDIT".
2. **Dato** lo stub Go generato, **quando** scrivo un test minimale che istanzia `SecurityContext{TenantId: "t1"}` e legge il campo, **allora** compila e il valore letto è `"t1"`.
3. **Dato** lo stub Python generato, **quando** importo `retrieval_pb2` e istanzio `SecurityContext(tenant_id="t1")`, **allora** l'import funziona e il campo è leggibile.
4. **Dato** il proto invariato, **quando** eseguo `task proto:gen` due volte di seguito, **allora** il secondo run non produce diff nel codice generato (idempotenza/determinismo del codegen).
5. **Dato** un ramo di prova che rimuove il campo `tenant_id` da `SecurityContext` (breaking change), **quando** eseguo `task proto:breaking`, **allora** il comando fallisce elencando la breaking change rilevata.
6. **Dato** un ramo di prova che aggiunge un nuovo campo con nuovo tag a un messaggio esistente (change additivo), **quando** eseguo `task proto:breaking`, **allora** passa.
7. **Dato** un ramo di prova con un errore di sintassi proto, **quando** eseguo `task proto:lint`, **allora** fallisce con il messaggio di buf che indica riga e motivo.

## 4. Errori & edge case

| Condizione | Comportamento atteso |
|---|---|
| Plugin `protoc-gen-go`/`protoc-gen-go-grpc` non installati | `task proto:gen` fallisce con istruzioni di installazione (`go install ...@latest`), non con un errore criptico di buf |
| `grpc_tools` non installato nel venv Python | fallisce con istruzione `pip install grpcio-tools` |
| Qualcuno modifica a mano un file in `libs/go/eci/retrieval/v1/` o l'equivalente Python | non prevenibile a livello di script in questo task; documentare nel CLAUDE.md locale di `libs/` che è generato e verrà sovrascritto — nessuna azione di enforcement automatico richiesta qui |
| `buf breaking` eseguito su un repo con un solo commit (nessun `main` da confrontare) | il comando deve fallire con messaggio chiaro ("no baseline"), non silenziosamente passare |

## 5. Non-goals
Non implementare il server gRPC reale (`RetrievalEngine`) — arriva in T1.4. Non generare stub per linguaggi diversi da Go/Python (Rust non consuma questo proto in Fase 0-5).

## 6. Vincoli dall'ADD

- Unit Python: `libs/py/eci_core/retrieval/v1/test_smoke.py` — stesso round-trip con `SerializeToString`/`ParseFromString`.

- Determinismo: step CI che esegue `task proto:gen` e verifica `git diff --exit-code` sulle directory generate (nessuna modifica inattesa).

## Deviazioni rispetto alla SPEC

1. **`contracts/proto/eci/retrieval/v1/retrieval.proto` mancante all'avvio**:
   il file D7 non era mai stato committato (gap nel commit "Step 2"); esisteva
   solo come file di lavoro non tracciato in `retrieval/v1/retrieval.proto`.
   Verificato byte-per-byte identico al blocco D7 dell'ADD consolidato, poi
   spostato nel path canonico sotto un ADR scritto dall'utente:
   `docs/decisions/ADR-0001-proto-retrieval-missing-commit.md`. Nessuna
   modifica di contenuto — solo path. `contracts/buf.gen.yaml`/`buf.yaml` sono
   file *nuovi* sotto `contracts/`: anche questi richiedono che l'ADR sia nello
   stesso commit quando si esegue `task guard`/CI (non ancora committato in
   questa sessione).

2. **`contracts/buf.yaml` — 3 regole di lint escluse**: il ruleset `DEFAULT`
   include `SERVICE_SUFFIX`/`RPC_REQUEST_STANDARD_NAME`/
   `RPC_RESPONSE_STANDARD_NAME`, che `retrieval.proto` (D7, non modificabile
   in questo task — SPEC §6) già viola per naming (`RetrievalEngine` invece di
   `RetrievalEngineService`, ecc.). Escluse esplicitamente via `lint.except`
   in `contracts/buf.yaml`; non toccano sintassi, breaking-check o
   `PACKAGE_DIRECTORY_MATCH`.

3. **Import assoluto errato nello stub Python generato**: `grpc_tools.protoc`
   genera `retrieval_pb2_grpc.py` con `from retrieval.v1 import retrieval_pb2`
   (basato sul path del proto passato a `-I`), non sul package Python di
   destinazione `eci_core.retrieval.v1`. `scripts/task-proto-gen.sh` applica
   un `sed` di post-processing sull'unica riga interessata subito dopo la
   generazione — stesso principio già previsto dalla SPEC per l'header
   "DO NOT EDIT" quando il tool non lo appone automaticamente da solo.

4. **File generati Python esclusi dal lint**: `ruff check` segnalava
   `retrieval_pb2.py`/`retrieval_pb2_grpc.py` (encoding comment superfluo,
   import non ordinati, import inutilizzato) — file generati, mai da
   correggere a mano. Esclusi via `extend-exclude` in `libs/py/pyproject.toml`
   (`*_pb2.py`, `*_pb2_grpc.py`).

5. **`libs/go` e `libs/py` diventano pacchetti installabili in questo task**:
   non erano previsti come moduli a sé nella SPEC-001 (solo placeholder). Per
   soddisfare l'Obiettivo §1 ("riutilizzabili... senza ulteriore lavoro di
   wiring") ho creato `libs/go/go.mod` (module
   `github.com/eci-project/eci/libs/go`) e `libs/py/pyproject.toml` (package
   `eci_core`, layout esplicito `eci_core/retrieval/v1/` con `__init__.py` a
   ogni livello — a differenza del bug di SPEC-001 dove `__init__.py` era al
   livello sbagliato). `scripts/task-build.sh`/`task-lint.sh`/`task-test.sh`
   estesi con lo stesso trattamento riservato ai servizi applicativi
   (venv dedicato per `libs/py`, build/vet/test diretti per `libs/go`).

6. **`libs/go/go.mod` richiede `go 1.25.0`**: emerso da `go mod tidy` per la
   catena di dipendenze di `google.golang.org/grpc` (richiede Go ≥1.25 per
   `protoc-gen-go-grpc` corrente); i moduli Go di `services/*` (SPEC-001)
   restano su Go 1.23. Nessun conflitto: sono moduli Go indipendenti; il
   toolchain 1.25 viene scaricato automaticamente da `go` (`GOTOOLCHAIN=auto`)
   quando serve.

7. **Tooling installato in user-space in questa sessione** (nessun sudo/pip di
   sistema disponibili, stesso vincolo di SPEC-001): `buf`, `protoc-gen-go`,
   `protoc-gen-go-grpc` via `go install` in `~/go/bin`; `.venv-tools/` a root
   con `grpcio-tools` per la generazione Python (creato con `virtualenv` per
   lo stesso motivo PEP 668 già documentato in SPEC-001). `.venv-tools/`
   aggiunto a `.gitignore`.

8. **`task proto:breaking` gira da `contracts/`** (`dir: contracts` nel
   Taskfile) **con `--against '../.git#branch=main,subdir=contracts'`**
   (path relativo alla working dir del comando) invece della forma letterale
   `'.git#branch=main,subdir=contracts'` di SPEC §2, che assume l'esecuzione
   dalla root del repo: con `buf.yaml`/`buf.gen.yaml` in `contracts/`, `buf`
   deve girare da lì per auto-scoprirli, quindi il riferimento al `.git`
   (che vive nella root) va risolto con `../`.

9. **CI**: nessun nuovo job separato — `proto:lint`/`proto:breaking` e il
   controllo di determinismo (`task proto:gen` + `git diff --exit-code`) sono
   step aggiunti al job `guard` esistente (SPEC-001), che ha già il checkout
   con `fetch-depth: 0` richiesto da entrambi (istruzione esplicita
   dell'utente: riusare, non duplicare quella configurazione).
